# Design

## Context

Проект greenfield: кода нет, есть только ТЗ `resources/vpn-chain-amneziawg-spec.md` — самодостаточное описание схемы (архитектура, шаблоны конфигов, правила обфускации, чек-лист приёмки, troubleshooting). Решения пользователя: нативное macOS-приложение на SwiftUI, полная автоматизация по SSH, аутентификация паролем и ключами. Приложение заменяет «ручной режим» ТЗ (bash-скрипты, запускаемые агентом на серверах), сохраняя схему и порядок шагов как источник истины. В артефактах учтены три исправления к ТЗ: rp_filter на интерфейсе `awg-relay`, имя контейнера всегда из детекта (не из DoD-хардкода), некорректная ссылка 9.3→«7.4» (в приложении порядок шагов задаётся движком, ссылки не нужны).

## Goals / Non-Goals

**Goals:**

- Один сценарий «подключил два сервера → нажал Установить → цепочка работает» с наблюдаемым пошаговым прогрессом.
- Строгое соответствие схеме ТЗ: порядок С2 → С1 → handshake, шаблоны 9.1/9.2, правила разделов 6.2/7, kill-switch.
- Безопасность: контейнер AmneziaVPN не трогается, SSH не блокируется, приватные ключи не покидают Mac (кроме записи в конфиги серверов) и не попадают в логи.
- Идемпотентность и обратимость: повторный запуск безопасен, uninstall удаляет только свои артефакты.

**Non-Goals:**

- Управление клиентской стороной AmneziaVPN на Mac (раздел 8 ТЗ — только инструкция в UI).
- Усиление до AmneziaWG 2.0/3.1 и ядерный модуль (разделы 12.1/12.2 ТЗ) — отдельные итерации.
- Цепочки из >2 серверов, несколько независимых установок (профили строго под одну пару С1/С2).
- Подпись/notarization и распространение App Store — сейчас локальный инструмент разработчика.

## Decisions

### D1. Каркас UI: SwiftUI, macOS 13+, MVVM, одно окно с sidebar
Навигация: Подключения / Установка / Статус и проверки / Клиент (инструкция) / Настройки. Локализация RU (язык пользователя), en — опционально позже.
*Альтернатива:* AppKit — больше кода без выгоды для такого объёма; Electron/Tauri — отклонены выбором пользователя (нативное).

### D2. SSH-транспорт: swift-nio-ssh (SPM)
Чистый Swift, интегрируется в async/await, поддерживает password- и key-auth. Обёртка `SSHClient`: connect (host/port/user/auth) → exec (команда, таймаут, стриминг stdout/stderr) → код возврата; один экземпляр на сервер, переиспользуемый всеми шагами.
*Альтернатива:* shelling `/usr/bin/ssh` — сохраняет поддержку RSA и agent, но пароли придётся вводить через tty-трюки, парсинг вывода ненадёжен, UX хуже. libssh2-обёртка — C-зависимость, сложнее сборка.
*Ограничение:* NIOSSH поддерживает ed25519/ECDSA/P-256 ключи, RSA — нет. См. риски R1.

### D3. Генерация секретов на Mac (CryptoKit), не на серверах
Приватный ключ WireGuard = 32 байта (клампинг `clamped[0] &= 24; clamped[31] &= 127; clamped[31] |= 64`) в base64; публичный — X25519 от приватного. Параметры обфускации генерируются локально по правилам раздела 4 (unit-тесты на каждое правило). Серверам отдаются только готовые конфиги; `awg genkey` на серверах не нужен. Приватные relay-ключи хранятся и в Keychain Mac (для повторного просмотра конфигов и сравнения концов), и в `/etc/amnezia/chain/` на серверах.

### D4. Движок provisioning: детерминированный конечный автомат шагов
Порядок фиксирован (вместо payload-подхода ТЗ, т.к. приложение имеет SSH-доступ к обоим серверам):
`Detect(C1) → Install(C2) → Install(C1) → Configure(C2) → Configure(C1) → ApplyRules(C1) → Verify(handshake)`.
Каждый шаг — check-then-apply: сначала сбор фактического состояния (`command -v`, `awg showconf`, `ip rule`, `docker inspect`), потом применение только недостающего. Отсюда идемпотентность, возобновление после сбоя и отсутствие «слепых» скриптов. Сложные блоки (правила firewall, юниты) доставляются heredoc-ом как файлы с маркером `managed-by: amnezia-chain`, после чего выполняются — не «cat | bash».

### D5. Состояние: на серверах `/etc/amnezia/chain/` (0700/0600), на Mac — UserDefaults (профили без секретов) + Keychain (пароли, парольные фразы, приватные relay-ключи)
Файл `env` на С1 — единственный источник истины о бридже/подсетях/commit/параметрах (как в ТЗ §6.2 шаг 2), что упрощает диагностику и повторные запуски без участия Mac.

### D6. Host key verification: TOFU с явным подтверждением
При первом подключении приложение показывает fingerprint сервера, пользователь подтверждает; отпечаток сохраняется в профиле, несовпадение при следующих подключениях — жёсткая ошибка без обхода.
*Альтернатива:* системный known_hosts — не переносим между пользователями Mac, конфликтует с Keychain-профилями.

### D7. Соответствие ТЗ с исправлениями
- rp_filter: `sysctl -w net.ipv4.conf.awg-relay.rp_filter=2` после подъёма интерфейса + `net.ipv4.conf.default.rp_filter = 2` в persist-файле (ядро берёт max(all, iface) — только `all` недостаточно).
- Имя контейнера нигде не хардкодится: всегда из детекта, передаётся во все шаги (включая проверки `docker exec`).
- Правила С1 — отбор клиентского трафика по метке `fwmark` (пакеты с интерфейса контейнера, кроме ответов клиентской VPN-сессии по порту источника) и `ip rule fwmark … lookup 51821`; правило по `iif` не применяется (интерфейс контейнера используется в обоих направлениях). При отсутствии цепочки `DOCKER-USER` (старый Docker/другая среда) — вставка в FORWARD с маркером + предупреждение в UI.
- Порт клиентского AWG обязателен для правил: без него установка останавливается до применения (иначе ответы контейнера клиентам уйдут в туннель).
- NAT: Docker на С1 NAT-ит подсеть контейнера (`! -o amn0`), поэтому для выхода в `awg-relay` SNAT отключается (`-o awg-relay -j RETURN` в `nat POSTROUTING`), а на С2 добавляется MASQUERADE для `10.99.0.0/24` — иначе трафик уходит в интернет с частным источником и ответы не возвращаются.

### D8. Диагностика как данные, не как код
Таблицы проверок (§10) и симптомов (§11) описаны декларативно (id, команда, парсер, ожидание, подсказка), поэтому новые проверки добавляются без изменения движка. Ручные пункты чек-листа (7–9, 11–12 §10) отображаются с инструкциями, результат — вручную пользователем.

## Risks / Trade-offs

- [R1. NIOSSH не поддерживает RSA-ключи — часть пользователей с классическими RSA-ключами не подключится] → Поддержка ed25519/ECDSA + парольная аутентификация; понятная ошибка с объяснением при RSA-ключе; в settings — ссылка на конвертацию `ssh-keygen -t ed25519`. Отложенная альтернатива: транспорт-плагин поверх `/usr/bin/ssh`.
- [R2. Сборка amneziawg-go на слабом сервере идёт долго, возможны таймауты SSH-сессии] → Стриминг вывода, generous-таймаут только на шагах сборки, шаг идемпотентен и возобновляем (`make` продолжается с места обрыва).
- [R3. Частичный сбой оставляет сервер в промежуточном состоянии] → check-then-apply на каждом шаге (D4); пользователь видит точный шаг сбоя; повторный запуск продолжает; uninstall откатывает.
- [R4. Ошибка в правилах маршрутизации может заблокировать host-трафик/SSH] → Маркируются только пакеты с интерфейса контейнера (кроме ответов клиентам), поэтому host-трафик и SSH не затрагиваются; в UI и в справке — rescue-команда для консоли провайдера (`while ip rule del table 51821; do :; done`).
- [R5. AmneziaVPN пересоздаёт Docker-сеть → устаревшие подсети в конфиге С2] → Диагностика сравнивает текущий детект с `env` на С1 и `AllowedIPs` на С2; при расхождении предлагает переприменение (ТЗ §11).
- [R6. Порядок С2 → С1 нарушать нельзя: при обратном порядке клиенты уйдут в blackhole до готовности выхода] → Порядок зашит в автомат; пользователь не управляет последовательностью шагов.
- [R7. UDP 51828 закрыт панелью провайдера — самая частая причина «нет handshake»] → Шаг проверки `nc -uvz` перед верификацией + явная подсказка про панель/sg провайдера в сводке.

## Migration Plan

Greenfield: миграции нет. Rollback любой установки — capability `chain-diagnostics` (uninstall). Обновление схемы из будущих версий ТЗ — новые изменения OpenSpec поверх specs этого изменения.

## Итоги приёмки (2026-11-12)

Приёмка на реальной паре: вход (Docker + AmneziaVPN, контейнер `amnezia-awg2` на сети `amn0`/`172.29.172.0/24`, клиентская подсеть `10.8.1.0/24`, порт клиентского AWG `44949`) и выход (`eth0`, публичный IP). Цепочка работает end-to-end: `2ip.ru` показывает IP сервера-выхода.

### Регрессии, найденные приёмкой и исправленные (все закрыты unit-тестами)

1. **`iif` ломал handshake клиентов**: интерфейс контейнера (`amn0`) используется в обоих направлениях, правило `ip rule iif` уводило ответы контейнера клиентам в relay-туннель. → отбор по `fwmark` с исключением `--sport <порт клиентского AWG>` (D7).
2. **SNAT Docker'а на входе**: правило `-s <docker-подсеть> ! -o amn0 -j MASQUERADE` подменяло источник туннельного трафика на `10.99.0.1`. → `-o awg-relay -j RETURN` первым в `nat POSTROUTING` на входе + MASQUERADE `10.99.0.0/24` на выходе.
3. **Порт клиентского AWG не определялся**: конфиг в новых AmneziaVPN — `awg0.conf`, а не `wg0.conf`. → мультипатовый поиск; без `ListenPort` установка останавливается до применения правил.
4. **`systemctl enable --now` — no-op для активных юнитов**: правила не переприменялись. → `enable` + `restart`.
5. **`PrivateKey` отсутствовал в шаблонах 9.1/9.2** — рендер конфигов его не вставлял.
6. Мелочи сборки на серверах: порядок Go toolchain-решений, `curl`+`ca-certificates`, уникальный heredoc-разделитель, shebang первой строкой маркерного скрипта, `bash -x` в диагностике падений.

### Отложенные проверки (пункт 8.2)

Kill-switch и reboot-персистентность не прогонялись (решение пользователя). Команды для будущего прогона:

- Kill-switch: на входе `systemctl stop awg-quick@awg-relay` → клиент без интернета, реальный IP не светится; `systemctl start awg-quick@awg-relay` → восстановилось.
- Reboot (сначала выход, потом вход; консоль провайдера — как запасной доступ): после загрузки на входе `systemctl is-active awg-quick@awg-relay vpn-chain.service`, `ip rule show | grep 51821`, `iptables -t mangle -S PREROUTING | grep VPNCHAIN_MARK`, `iptables -t nat -S POSTROUTING | grep 'awg-relay -j RETURN'`; на выходе `systemctl is-active awg-quick@awg-relay vpn-chain-exit.service`; затем клиент — `2ip.ru` = IP выхода.

Замечание по UX (вне скоупа изменения): на экране «Подключения» нет кнопки сброса профиля/секретов — слоты перезаписываются сохранением; `clearSecrets()` в ViewModel уже есть, кнопка не подключена.
