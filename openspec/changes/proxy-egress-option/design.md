# Design

## Context

Маршрутизация relay-туннеля на сервере-входе уже построена на `fwmark 0x51 → таблица 51821 → default dev awg-relay + blackhole` (`ConfigureC1.renderRulesScript`). Сегодня маркируется только клиентский трафик из моста контейнера AmneziaVPN (`VPNCHAIN_MARK` в mangle PREROUTING). Опция из issue #8 добавляет источник маркировки для Docker-контейнеров сервера-входа (mangle PREROUTING по bridge сетей) и SNAT их подсетей в туннель. Правила применяются идемпотентными bash-скриптами с маркером `# managed-by: amnezia-chain`, персистентность — systemd-юнитами. Детект окружения (`EnvironmentDetection`) уже умеет разбирать `docker network inspect`.

## Goals / Non-Goals

**Goals:**
- Переиспользовать существующую маркировку/таблицу 51821 — только новый источник MARK и SNAT.
- Не менять настройки сервера-выхода и его Docker.
- Идемпотентность, детект без хардкода, полный откат по маркеру, kill-switch blackhole.
- UI-раздел «Прокси» и диагностика в существующих паттернах (DesignSystem, ChecksEngine).

**Non-Goals:**
- Установка/настройка самих прокси-сервисов (Xray/3x-ui, Shadowsocks, MTProto).
- Проксирование хостового трафика сервера-входа (осознанно сужено в ходе приёмки).
- Индивидуальные правила на процесс/прокси — только режим + исключения сетей.
- IPv6 в relay-туннеле, TPROXY.

## Decisions

### D1. Отдельный модуль `ProxyEgress` вместо расширения ConfigureC1/C2
Рендер правил режима — новый файл `Sources/VPNChainCore/Provisioning/ProxyEgress.swift` (`ProxyEgressRules`): вход (`renderEntryScript`) и выход (`renderExitScript`). Оба скрипта режима — отдельные файлы с собственными юнитами: `/usr/local/bin/vpn-chain-proxy-rules.sh` + `vpn-chain-proxy.service` (С1) и `/usr/local/bin/vpn-chain-proxy-exit-rules.sh` + `vpn-chain-proxy-exit.service` (С2). Альтернатива — вплести правила в существующие скрипты/юниты — отвергнута: выключенный режим не должен менять содержимое уже установленных скриптов (совместимость с парами, установленными до опции).

### D2. Область режима — только Docker-сети
`VPNCHAIN_DOCKER_OUT` (mangle PREROUTING): RETURN для `--ctdir REPLY`, приватных сетей и IP выхода; затем по `-i <bridge>` каждой включённой сети `MARK 0x51`. Хостовые цепочки (`VPNCHAIN_HOST_OUT` в OUTPUT) из ранней версии больше не создаются: режим не должен заворачивать обновления пакетов, `docker pull` и DNS сервера-входа. Снятие хостовых цепочек сохранено в скрипте выключения для миграции. Значения (bridge, IP выхода, метка, таблица) — из детекта и констант `ConfigureC1`.

### D3. SNAT на входе вместо маршрутов/NAT на выходе
Для каждой включённой подсети на входе добавляется `MASQUERADE -s <subnet> -o awg-relay` (вставляется в начало `nat POSTROUTING`, перед существующим `RETURN -o awg-relay`). Relay-туннель использует cryptokey routing: пакеты с адресами источника вне `AllowedIPs` молча отбрасываются. SNAT приводит источник к адресу туннеля (`10.99.0.1`), который разрешён обеим сторонам, поэтому:
- на сервере-выходе не нужны ни маршруты, ни MASQUERADE для подсетей входа;
- исчезает конфликт одинаковых Docker-подсетей (у входа и выхода по умолчанию `172.17.0.0/16`);
- старые правила прежней схемы (маршрут + MASQUERADE) снимаются по списку из `proxies.json`.

### D4. Состояние — `/etc/amnezia/chain/proxies.json`
JSON: `{ "managed-by": "amnezia-chain", "enabled": bool, "exitIP": "...", "networks": [{"name","subnet","bridge"}] }`, права 0600. Пишется на обоих серверах. Отсутствие файла = выключено (совместимость). Настройка в приложении — `ProxyEgressSettings` (enabled, excludedNetworks) в профиле (`ProfileStore`); UI-состояние не источник истины для серверов.

### D5. Порядок применения и откат — шаги ProvisioningEngine
Шаги: `proxy-exit` (С2: очистка следов прежней схемы и состояние) → `proxy-entry` (С1: маркировка, SNAT, IPv6, состояние). При ошибке на `proxy-entry` выполняется `proxy-disable` (снятие на обоих по `proxies.json`), режим остаётся выключенным, ошибка показывается с шагом, кодом выхода и журналом. Выключение = применение «пустого» списка с enabled=false.

### D6. IPv6-kill-switch — только контейнеры, таблица mangle
При включённом режиме в `mangle PREROUTING` создаётся `VPNCHAIN_PROXY6_DOCKER`: RETURN для `--ctdir REPLY` и link-local, DROP для `-i <bridge>` включённых сетей. Цепочка обязательно в `mangle`: `PREROUTING` в filter-таблице не существует, и вставка туда роняет скрипт (`ip6tables: No chain/target/match by that name`). Хостовой IPv6 не блокируется — хост вне области режима.

### D7. Детект сетей и IP выхода
`ProxyNetworkDetector`: список Docker-сетей через `docker network ls` + `docker network inspect` (имя, подсеть, bridge), публичный IP выхода (`curl -4 … api.ipify.org`). Сеть AmneziaVPN определяется объединением сигналов — сети контейнера AmneziaVPN и сеть с bridge, равным `BRIDGE` из env, — за вычетом дефолтной `bridge`. Причина: на реальной паре `BRIDGE=amn0` (интерфейс контейнера, не Docker), а контейнер подключён сразу к своей сети и к `bridge`; исключение всех сетей контейнера скрывало прокси, живущие в `bridge`.

### D8. Диагностика
Три новые проверки в `ChecksEngine` (`proxy-docker-networks`, `proxy-nat-tunnel`, `proxy-egress-ip`), активные только при включённом режиме. Две записи в `Troubleshooting`. `UninstallPlan` снимает proxy-цепочки, IPv6-блокировку и SNAT по `proxies.json`. Ошибки применения показываются через `UserMessages` с шагом, кодом выхода и хвостом журнала.

## Risks / Trade-offs

- [Хостовые прокси не покрываются режимом] → осознанное сужение по итогам приёмки: хостовой трафик (обновления, DNS) остаётся вне туннеля; при необходимости вернуть — отдельная опция.
- [Пересоздание Docker-сети меняет bridge → правила молча не работают] → проверка `proxy-docker-networks` ловит дрейф; повторное применение пересчитывает bridge.
- [Маркировка моста Amnezia] → в `VPNCHAIN_DOCKER_OUT` сохранены исключения по `CLIENT_PORT` и REPLY; сеть Amnezia исключается из списка.
- [SNAT меняет источник — часть протоколов с проверкой адреса может не работать] → для прокси-сервисов не критично; откат — выключение режима.
- [Провайдер сервера-выхода может фильтровать отдельные назначения] → ограничение окружения, не кода; фиксируется в приёмке (например, DPI на 443 к Telegram-диапазонам обходится FakeTLS на стороне прокси).

## Migration Plan

Изменение аддитивное: без включения режима серверы не меняются. Повторное применение на паре с прежней версией снимает хостовые цепочки и старые маршруты/NAT выхода. Откат — выключить режим в UI. Релиз 0.3.0, опция выключена по умолчанию.

## Acceptance Findings (реальная пара, 2026-11-12)

- Хостовый и контейнерный egress через выход подтверждены (`curl --socks5-hostname … http://api.ipify.org` → IP выхода; google 200, ~87 КБ данных, TLS).
- `BRIDGE=amn0` — не Docker-bridge; контейнер AmneziaVPN подключён к `amnezia-dns-net` и `bridge`. Потребовало D7 (объединение сигналов).
- IPv6-цепочка в filter-таблице роняла скрипт; исправлено на `mangle` (D6).
- Маршруты/NAT на выходе перекрывали Docker-подсеть выхода и не помогали из-за cryptokey routing; заменено на SNAT (D3).
- Провайдер выхода фильтрует 443 к Telegram-диапазонам (прямые тесты нестабильны, порт 80 отвечает); рабочий обход на стороне прокси — FakeTLS. Цепочка при этом исправна.

## Open Questions

- Возвращать ли хостовое проксирование отдельной под-опцией (для systemd-прокси, не в Docker).
- Способ проверки egress для контейнеров без curl/wget (сейчас — ручная проверка через прокси).
