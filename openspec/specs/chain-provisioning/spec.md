# chain-provisioning Specification

## Purpose

Автоматически разворачивает relay-цепочку «Клиент → С1 (AmneziaVPN) → С2 → Интернет» из ТЗ `resources/vpn-chain-amneziawg-spec.md` на паре серверов по SSH: детект окружения, установка ПО, конфигурация туннеля, правил и юнитов — идемпотентно и без ручного выполнения команд.

## Requirements

### Requirement: Детект окружения Сервера 1
Перед установкой приложение SHALL определить на С1 контейнер AmneziaWG, Docker-сеть, её подсеть и IP контейнера, интерфейс контейнера (`amn*`, иначе `ip route get <IP контейнера>`), клиентскую подсеть и порт клиентского AWG из конфига в контейнере. Клиентская подсеть определяется «мягко»; неизвестный порт блокирует применение правил. Значения SHALL сохраняться в состоянии на С1.

#### Scenario: Контейнер найден
- **WHEN** на С1 запущен Docker и найден контейнер amnezia-awg
- **THEN** приложение показывает имя контейнера, интерфейс входа, Docker-подсеть и IP контейнера и переходит к следующему шагу

#### Scenario: Новая топология AmneziaVPN
- **WHEN** на хосте С1 есть интерфейс `amn*` (AWG-интерфейс поднят на хосте)
- **THEN** интерфейсом контейнера выбирается `amn*`, и правила `iptables -i`/маркировка применяются к нему

#### Scenario: Старая топология AmneziaVPN
- **WHEN** хост-интерфейса `amn*` нет
- **THEN** интерфейсом входа выбирается интерфейс из `ip route get <IP контейнера>` (Docker-бридж `br-…`/`docker0`)

#### Scenario: Контейнер отсутствует
- **WHEN** Docker не установлен или контейнер AmneziaWG не найден
- **THEN** установка останавливается с сообщением «сначала установите AmneziaWG из приложения AmneziaVPN» без изменения сервера

#### Scenario: Клиентская подсеть не определена
- **WHEN** конфиг AWG недоступен внутри контейнера
- **THEN** установка продолжается: клиентская подсеть просто не включается в конфигурацию С2

#### Scenario: Конфиг AWG найден
- **WHEN** внутри контейнера есть `awg0.conf` или `wg0.conf` в `/opt/amnezia/awg` либо `/etc/amnezia/awg`
- **THEN** из `Address` определяется клиентская подсеть, из `ListenPort` — порт клиентского AWG

### Requirement: Автоматический перенос контейнера с дефолтного bridge
Если рабочая сеть контейнера AmneziaWG — дефолтная `bridge` (подсеть 172.17.0.0/16 присутствует почти на любом сервере с Docker и коллидируется с сетями сервера-выхода), приложение SHALL автоматически создать выделенную сеть `amnezia-relay-net` со свободной подсетью (не занятой маршрутами ни на одном из серверов), подключить к ней контейнер и отключить от `bridge`, после чего пересчитать окружение (подсеть, IP, интерфейс хоста) по новой сети.

#### Scenario: Контейнер на дефолтном bridge
- **WHEN** при детекте рабочей сетью контейнера выбрана `bridge`
- **THEN** приложение создаёт `amnezia-relay-net` со свободной подсетью, подключает контейнер к ней, отключает от `bridge` и продолжает установку с подсетью/интерфейсом новой сети

#### Scenario: Контейнер уже в кастомной сети
- **WHEN** рабочая сеть контейнера отличается от `bridge`
- **THEN** миграция не выполняется, установка идёт по текущей сети

### Requirement: Установка недостающих компонентов из одного commit
Приложение SHALL проверять наличие `awg`, `awg-quick`, `amneziawg-go` на каждом сервере и устанавливать только недостающие компоненты. Сборка SHALL выполняться из одного зафиксированного commit репозиториев, одинакового на обоих серверах; хэш SHALL сохраняться в состоянии установки.

#### Scenario: ПО уже установлено
- **WHEN** повторный запуск выполняется на сервере, где `awg`, `awg-quick` и `amneziawg-go` уже собраны из нужного commit
- **THEN** шаг установки пропускается без повторной сборки

#### Scenario: Один commit на обоих серверах
- **WHEN** установка ПО выполняется на С1 и С2
- **THEN** оба сервера собираются из одного и того же commit, что гарантирует совместимость версий протокола на концах

### Requirement: Fallback при старом системном Go
Если системный Go младше версии, требуемой `go.mod` репозитория amneziawg-go, приложение SHALL установить актуальный Go из официального tarball в `/usr/local/go` и выполнить сборку им, не удаляя системный Go.

#### Scenario: Старый системный Go
- **WHEN** версия системного Go ниже требуемой в `go.mod` репозитория amneziawg-go
- **THEN** свежий Go скачивается с go.dev в файл, распаковывается в `/usr/local/go`, и сборка выполняется им; системный Go остаётся на месте

### Requirement: Проверка совместимости окружения
Приложение SHALL проверять ОС и архитектуру каждого сервера перед установкой и останавливать установку при неподдерживаемой комбинации с понятным сообщением.

#### Scenario: Неподдерживаемое окружение
- **WHEN** ОС сервера не входит в Debian 11/12/13 и Ubuntu 20.04/22.04/24.04 либо архитектура не x86_64/aarch64
- **THEN** установка на этом сервере не начинается, приложение сообщает причину

### Requirement: Конфигурация relay-туннеля С1
Приложение SHALL создать на С1 конфиг `/etc/amnezia/amneziawg/awg-relay.conf` по шаблону ТЗ 9.1: адрес `10.99.0.1/24`, `Table = off`, `MTU = 1420`, параметры обфускации, без `ListenPort`, пир С2 с `Endpoint = <С2>:51828`, `AllowedIPs = 0.0.0.0/0` и `PersistentKeepalive = 25`. Приложение SHALL включить юнит `awg-quick@awg-relay`.

#### Scenario: Конфиг создан
- **WHEN** шаг конфигурации С1 выполняется впервые
- **THEN** на С1 появляется конфиг с `Table = off`, параметрами обфускации и Endpoint на С2:51828, и интерфейс `awg-relay` поднимается через `awg-quick@awg-relay`

### Requirement: Ручной юнит awg-quick при отсутствии
Если после сборки amneziawg-tools юнит `awg-quick@.service` не установлен, приложение SHALL создать его по шаблону ТЗ 9.4 с переменной `WG_QUICK_USERSPACE_IMPLEMENTATION=amneziawg-go`.

#### Scenario: Юнит awg-quick отсутствует
- **WHEN** `systemctl cat awg-quick@.service` не находит юнит
- **THEN** приложение создаёт юнит по шаблону ТЗ 9.4 с `WG_QUICK_USERSPACE_IMPLEMENTATION=amneziawg-go`, и `awg-quick@awg-relay` запускается через userspace-демон

### Requirement: Конфигурация relay-туннеля С2
Приложение SHALL создать на С2 конфиг `/etc/amnezia/amneziawg/awg-relay.conf` по шаблону ТЗ 9.2: адрес `10.99.0.2/24`, `ListenPort = 51828`, `MTU = 1420`, те же параметры обфускации, пир С1 с `AllowedIPs` из внутренних подсетей (relay-подсеть, Docker-подсеть С1, при наличии — клиентская). `AllowedIPs` пира на С2 MUST NOT содержать `0.0.0.0/0`.

#### Scenario: Конфиг С2 создан
- **WHEN** шаг конфигурации С2 выполняется
- **THEN** на С2 появляется конфиг с `ListenPort = 51828` и `AllowedIPs` только из внутренних подсетей, без `0.0.0.0/0` — иначе С2 завернул бы собственный SSH-трафик в туннель

### Requirement: Правила выхода и их персистентность
Приложение SHALL применить на С2 правила выхода: `ip_forward` с persist в `/etc/sysctl.d/99-vpn-chain.conf`, разрешение UDP 51828 на INPUT, MSS clamp, FORWARD-правила для `awg-relay ↔ WAN` и MASQUERADE по подсетям С1 (Docker-подсеть, клиентская при наличии) **и по relay-подсети `10.99.0.0/24`** (Docker на С1 делает SNAT в адрес туннеля), и SHALL обеспечить восстановление правил после перезагрузки.

#### Scenario: Правила выхода применены и переживают reboot
- **WHEN** правила выхода применены и сервер С2 перезагружается
- **THEN** после загрузки INPUT/FORWARD/MASQUERADE-правила и `ip_forward` восстановлены автоматически

### Requirement: Policy routing только для клиентского трафика
Приложение SHALL отбирать клиентский трафик на С1 по **метке**: в `mangle PREROUTING` маркируются пакеты с интерфейса контейнера, кроме ответов клиентской VPN-сессии (`--sport <порт клиентского AWG>`), а `ip rule fwmark <метка> lookup 51821` направляет их в таблицу с `default dev awg-relay` и `blackhole default metric 42760`. Правило по `iif` и SNAT в адрес туннеля MUST NOT использоваться. Прежние правила таблицы 51821 SHALL удаляться.

#### Scenario: Правила затрагивают только клиентский трафик
- **WHEN** правила применены на С1
- **THEN** в `ip rule` присутствует правило с `fwmark`, а SSH-сессия С1, host-трафик и подключение клиентов работают при поднятом и при упавшем туннеле

#### Scenario: Ответы контейнера клиентам не попадают в туннель
- **WHEN** клиент AmneziaVPN подключается к серверу-входу
- **THEN** пакеты контейнера с портом источника клиентского AWG не маркируются и доставляются клиенту — handshake завершается

#### Scenario: Порт клиентского AWG не определён
- **WHEN** в конфиге контейнера не удалось найти `ListenPort`
- **THEN** установка останавливается с сообщением о невозможности безопасно применить правила, правила не применяются

#### Scenario: SNAT в адрес туннеля отключён
- **WHEN** клиентский трафик уходит в `awg-relay`
- **THEN** в `nat POSTROUTING` первым стоит `-o awg-relay -j RETURN`, и исходный адрес сохраняется до сервера-выхода

#### Scenario: Клиентский трафик доходит до интернета
- **WHEN** relay-туннель поднят и клиент подключён к серверу-входу
- **THEN** источник клиентского трафика не подменяется адресом туннеля на С1, на С2 трафик из туннеля NAT-ится во внешний интерфейс, и внешний IP клиента равен адресу сервера-выхода

#### Scenario: Kill-switch срабатывает
- **WHEN** туннель `awg-relay` остановлен на С1 (`systemctl stop awg-quick@awg-relay`) и клиент пытается выйти в интернет
- **THEN** трафик клиентов блокируется (blackhole), и реальный IP клиента не светится; после `start` цепочка снова работает

### Requirement: Firewall-правила и анти-утечка IPv6
Приложение SHALL добавлять правила firewall собственной цепочкой в `DOCKER-USER` (MSS clamp, разрешение `бридж → awg-relay`, возврат RELATED,ESTABLISHED) и DROP-правило для IPv6-трафика клиентов в `ip6tables`. Приложение SHALL включать `ip_forward` с persist и выставлять `rp_filter = 2` на интерфейсе `awg-relay` и в persist-файле (`net.ipv4.conf.default.rp_filter = 2`).

#### Scenario: rp_filter применён на интерфейсе
- **WHEN** правила применены на С1
- **THEN** `net.ipv4.conf.awg-relay.rp_filter = 2` установлен, и persist-файл содержит `net.ipv4.conf.default.rp_filter = 2`, так что ответы из туннеля не режутся строгим фильтром интерфейса

#### Scenario: IPv6-утечка предотвращена
- **WHEN** правила применены на С1
- **THEN** IPv6-трафик клиентов из бриджа блокируется в `ip6tables` (цепочка `VPNCHAIN6` в `DOCKER-USER`)

### Requirement: Идемпотентное применение правил С1
Применение правил SHALL быть оформлено как идемпотентный скрипт `/usr/local/bin/vpn-chain-rules.sh` с юнитом `vpn-chain.service`, запускаемым после `docker.service` и `awg-quick@awg-relay.service`, чтобы правила восстанавливались после перезагрузки и пересоздания цепочек Docker.

#### Scenario: Правила восстановлены после перезагрузки или перезапуска Docker
- **WHEN** сервер С1 перезагружается или Docker пересоздаёт цепочки
- **THEN** запуск `vpn-chain.service` восстанавливает правила без дублей, и цепочка снова работает

### Requirement: Порядок развёртывания и проверка handshake
Приложение SHALL выполнять развёртывание в порядке: С2 (конфиг + правила выхода) → С1 (конфиг + policy routing) → проверка handshake между С1 и С2. Установка SHALL считаться успешной только после появления handshake (`awg show awg-relay` на С1) в пределах таймаута.

#### Scenario: Handshake получен
- **WHEN** все шаги применены и на С1 появляется handshake с С2
- **THEN** приложение показывает успешное завершение установки с сводкой (бридж, подсети, порт) и подсказкой открыть UDP 51828 в панели провайдера С2

#### Scenario: Handshake отсутствует
- **WHEN** в пределах таймаута handshake не появился
- **THEN** установка помечается незавершённой, а приложение показывает диагностические проверки: доступность UDP 51828 (`nc -uvz`), совпадение параметров обфускации (`awg showconf awg-relay` с обоих концов), совпадение commit сборки amneziawg-go

### Requirement: Идемпотентность и безопасность изменений серверов
Повторный запуск установки SHALL быть безопасным: существующие ключи и параметры переиспользуются, изменяются только артефакты с маркером `# managed-by: amnezia-chain`, перед перезаписью создаётся резервная копия. Контейнер `amnezia-awg` и его конфиг MUST NOT модифицироваться. Приватные ключи MUST NOT выводиться в stdout/журнал приложения.

#### Scenario: Повторный запуск установки
- **WHEN** установка выполняется повторно на уже настроенной паре серверов
- **THEN** ключи и параметры не меняются, правила обновляются только у объектов с маркером, и цепочка остаётся рабочей без разрыва handshake

#### Scenario: Контейнер приложения не затронут
- **WHEN** установка (или повторный запуск) завершена на С1
- **THEN** `docker exec <имя из детекта> awg show` работает, рукопожатия клиентов приложения сохранены, конфиг контейнера не изменён

#### Scenario: Частичный сбой шага
- **WHEN** шаг установки завершается ошибкой в середине
- **THEN** уже применённые шаги остаются консистентными (каждый шаг идемпотентен), повторный запуск продолжает с места сбоя без дублирования артефактов
